# 프로필 저장·향후 Google 동기화 설계 제안

2026-11-04 후속 단계: 이 문서는 로컬 프로필 단계의 합의 기록이다. Google 재개발 승인 후의 현행 구현은 [Google 계약](./google-drive-sync-contract.md)과 [재개발 검증](../../docs/development/google-sync-verification.md)을 따른다. 아래 “향후/현재 중지”는 당시 로컬 프로필 단계의 시점이며, 옛 전송 형식을 다시 활성화한다는 뜻이 아니다.

## 동기화 범위 확정

이번 작업 단위의 Google 동기화 대상은 프로필·숙제·휴대 가능한 환경설정이다. 모험일지의 수익·지출·득템·보스·수동 기록은 로컬 DB에만 저장하고 업로드/다운로드하지 않는다. 같은 프로필을 두 PC에서 사용해도 모험일지는 각 PC에 별도로 남으며 원격 합산하지 않는다. 아래 과거 검토 중 모험일지 전송·PC 간 합산 예시는 향후 확장 가능성에 대한 참고이며 이번 구현·검증 범위에서 제외한다. 로컬 profile_id와 고유 기록 ID의 필요성은 원격 전송 여부와 별개다.



상태: 로컬 저장·이전·PC별 변경 파일·시간 기준·예외 충돌·보관 정책의 사용자 선택 확정. 로컬 저장과 일반 부팅/기록 경계를 구현했고 실제 게임·설치 업데이트 검증은 남아 있다. 새 Google 전송 프로토콜과 성능 수치는 향후 동기화 개발 때 검증한다.

## 최우선 설계 전제 — 기존 동기화 구현에 종속하지 않음

사용자 확정: 향후 Google 동기화는 기존 개발 내용을 재사용/수선하는 방식이 아니라 새로 개발한다. 현재 코드·기존 원격 파일 형식·operation 형식·상태 파일·동기화 계획서의 구조는 새 설계의 제약이 아니다. 호환을 위해 현재 구현에 맞춘 저장 구조를 만들지 않는다.

- 지금 결정할 대상은 로컬 프로필·숙제·설정·기록의 올바른 원본과 저장 원자성이다.
- 향후 동기화는 이 데이터 모델을 바탕으로 별도 프로토콜을 설계한다. 아래 outbox/원격 revision 등은 새 설계 후보이며 기존 클래스나 파일을 재사용하라는 요구가 아니다.
- 기존 사용자 숙제·설정·모험일지 보존 요구는 유지한다. 기존 사용자 데이터 이전과 옛 동기화 코드/통신 형식 호환은 별개다.
- 기존 원격 데이터를 자동으로 읽어 새 데이터에 합치는 동작을 가정하지 않는다. 옛 동기화 데이터의 가져오기·폐기 여부는 향후 명시적 정책으로 결정한다. 현재 검토 작업에서 원격 데이터를 삭제하거나 변경하지 않는다.

## 이미 확정한 사용자 요구

- 프로필 하나는 캐릭터 하나. 숙제·캐릭터 환경설정은 프로필별 관리.
- 서버는 기존 userServer와 동일한 단일 값. 새로운 별도 서버 속성을 중복 저장하지 않는다.
- 모험일지는 하나의 DB에 두고 원본 기록에 profile_id를 부여하여 전체/프로필별 조회.
- PC별 마지막 사용/현재 선택 프로필은 게임 진입 시 명시적 선택을 대신하지 않는다.
- 기존 다중 캐릭터는 데이터와 사용자 설정값을 복사하고 빈 기본 프로필을 재사용한다.
- 현재 Google 동기화는 중지하고 이후 개선 시 연동한다. 이번 작업에서 네트워크 동기화를 활성화하지 않는다.

## 참고 조사 — 새 구조의 제약으로 사용하지 않음

- config.ts는 config.json을 원자 교체하며 대부분의 숙제와 설정이 여기에 있다.
- diaryDb.ts는 단일 diary.db에 일지와 관련 로그를 저장한다.
- cloudSyncState.ts는 deviceId, generationId, base snapshot과 숙제 outbox를 cloud-sync-state.json에 별도로 보관한다.
- googleDriveSync.ts의 현재 원격 파일은 설정/숙제/meta JSON으로 분리되어 있다. 기존 원격 파일 이름/스키마를 새 프로필 형식에 그대로 재사용해서는 안 된다.
- backupManager.ts는 SQLite 및 설정 파일을 staging/rollback journal을 통해 복원한다.
- .agents/GOOGLE_DRIVE_SYNC_PLAN.md의 과거 단일 원격 JSON 제안은 현재 구현과 다르므로 새 구조의 사실 근거로 사용하지 않는다.

## 저장 방식 비교

| 방식 | 장점 | 주요 비용 |
|---|---|---|
| config.json에 모든 프로필 포함 | 초기 구현 변경이 적음 | 프로필 하나를 수정해도 전체 재저장. 비활성 프로필 유실/덮어쓰기와 동시성 관리가 복잡함 |
| profiles/<id>/settings.json + checklist.json | 사람이 보기 쉽고 프로필별 내보내기 쉬움 | 여러 파일의 변경·일지 기록·outbox를 함께 확정하기 위한 별도 journal/복구 절차 필요 |
| 단일 SQLite에 프로필·숙제·설정·일지·변경 대기 저장 | 같은 트랜잭션으로 원본과 변경 대기를 함께 확정. 프로필별/전체 조회와 데이터 무결성에 유리 | 기존 config 기반 기능과 localStorage 사용처를 저장 계층으로 연결해야 함 |

사용자 확정: 기기 전용 설정은 config.json에, 프로필·휴대 가능한 공통 설정·숙제·일지·미배정 기록·변경 이력은 하나의 SQLite DB에 저장하는 혼합 구조. JSON은 기기 설정 및 백업/공유/향후 동기화 교환 형식으로 사용한다. 구현 편의를 위해 파일과 DB에 같은 값을 각각 원본으로 두지 않는다.

## 확정 로컬 원본 구성 (보조 파일은 상세 설계 시 결정)

```text
twOverlay/
  config.json                 # 기기 전용 설정: 경로, 창 배치 등
  app-data.db                 # 프로필, 휴대 가능한 설정, 숙제, 일지와 변경 이력 원본
  device-state.json           # 기기 식별·선택창 상태 등 기기 전용 메타데이터
  sync/                       # 향후 새 동기화 구현의 기기 전용 메타데이터 (상세 미정)
  google_auth.enc             # 기존 인증 보관, 동기화 대상 아님
  custom_fonts/               # 기존 사용자 리소스
  custom_sounds/
  backups/                    # 일관된 로컬 스냅샷과 복원 journal
```

- 새 원본 파일명은 app-data.db로 한다. 기존 diary.db를 안전한 SQLite 백업 방식으로 복제한 staging DB에 새 구조를 적용하고, 검증 후 전환한다. 단순 실행 중 파일 복사로 WAL의 미반영 기록을 누락하지 않는다. SQLite WAL/SHM은 독립 동기화하지 않는다.
- 기기 전용 상태와 인증은 원격에서 가져온 값으로 교체하지 않는다.
- “모든 프로필에 공통”과 “모든 PC에 동기화”는 별개다. 공통 설정도 키별로 휴대 가능/기기 전용 여부를 정의한다.
- userServer는 프로필 설정 한 곳에만 저장한다. 기존 config.load().userServer는 선택 프로필을 읽는 호환 조회로 제공하고 config.json에 독립 원본으로 재저장하지 않는다.
- 저장은 메인 프로세스의 단일 저장 계층을 통해 수행한다. renderer/worker가 직접 파일을 수정하거나 프로필 전체 객체를 덮어쓰지 않는다.

## 제안 DB 논리 구조

| 영역 | 예시 테이블 | 역할 |
|---|---|---|
| 프로필 | profiles | UUID, 표시 이름, 생성/수정/삭제 상태. 서버는 profile_settings.userServer를 참조 |
| 환경설정 | profile_settings, shared_settings | 허용된 키·타입·범위와 버전. 기기 전용 키와 분리 |
| 숙제 | profile_homework_definitions, profile_homework_states | 프로필별 정의·정렬·최대 횟수와 주기별 횟수·N/A·완료 시각 |
| 일지 | 기존 activity_logs, homework_logs 등 | profile_id 및 안정적인 기록 ID. NULL은 기존 미지정 기록 |
| 집계 | 일지 집계 테이블/조회 | 날짜·프로필 기준 집계. 원본 로그에서 재계산 가능 |
| 미배정 | pending_profile_events | 원래 시각·세션·고유 이벤트 ID와 귀속 대기. 앱 종료 후 보존 |
| 변경 이력 | local_operations/outbox | 같은 트랜잭션에서 원본과 함께 기록되는 미전송 변경 |
| 이전 | migrations, legacy_character_profile_map | 일회성 이전 및 캐릭터→프로필 대응. 재시도 멱등성 |

세부 DDL/인덱스는 다음 설계 단계에서 확정한다. 모든 테이블에 무조건 profile_id를 추가하지 않고 기록 소유권이 있는 테이블과 앱 공통 테이블을 구분한다.

## 원자 저장과 실패 규칙

- 숙제/환경설정/기록 수정과 해당 변경 operation을 하나의 DB 트랜잭션으로 저장한다. 저장 실패 시 둘 다 반영하지 않는다.
- UI 성공 표시는 commit 이후에만 보낸다. 프로필 전환은 이전 쓰기 완료 및 새 설정 로드 성공 뒤 확정한다.
- 메모리 config는 조회 호환 계층이며 원본이 아니다. 프로필 객체 전체를 캐시에서 주기적으로 역저장하지 않는다.
- 로컬 저장은 인터넷 연결과 무관하게 완료된다. 향후 업로드 성공은 outbox ACK만 갱신하며 원본의 더 최신 변경을 되돌리지 않는다.
- JSON이 필요한 기기 설정은 기존 fsync+임시 파일 원자 교체를 유지한다. DB와 동시에 변경할 수밖에 없는 마이그레이션은 manifest/journal로 중단 복구한다.

## 향후 Google 교환 형식 제안

로컬 파일 배치를 그대로 복제하지 않고 버전 있는 JSON payload를 생성한다. 첫 배포에서는 향후 확장을 위한 구조만 준비하며 송수신하지 않는다.

- Google 동기화 파일 구성과 schema는 처음부터 새로 설계한다. 기존 settings/checklist/meta 분할이나 operation 구조를 따를 필요가 없다.
- 목록과 프로필 데이터는 논리적으로 구분한다: 프로필 UUID/삭제 표식 목록, 프로필별 설정·숙제 변경, 공통 휴대 가능 설정.
- 원격 프로필별 스냅샷과 변경 묶음에는 schemaVersion, profileId, operationId, deviceId, 기기별 증가 순번, 기준 revision을 포함한다. 이름/서버/활성 프로필만으로 병합 대상을 결정하지 않는다.
- ID는 로컬 DB 자동 증가 숫자 대신 기기 간 유지되는 UUID를 사용한다. 동일 서버·이름의 프로필이 다른 기기에서 독립 생성된 경우 자동으로 하나로 합치지 않고 연결/중복 정리 정책을 둔다.
- PC A의 활성 프로필이 PC B의 활성 프로필을 변경하지 않는다. 선택 상태는 기기 전용이다.
- 원격 저장은 조건부 갱신 및 충돌 재조회/병합을 사용한다. 파일 누락·충돌을 발견했다고 최신 로컬 상태로 무조건 새 파일을 만들지 않는다.
- 여러 원격 파일을 원자 교체할 수 있다고 가정하지 않는다. revision별 불변 snapshot을 먼저 업로드하고 목록 manifest가 완료된 revision을 가리키게 하는 게시 방식을 검토한다. 중단 시 이전 완료 revision으로 읽을 수 있어야 한다.
- 향후 모험일지 동기화는 DB 바이너리 전체 업로드 대신 안정적인 기록 ID/변경 이력을 교환하도록 준비한다. 실제 동기화 범위·보관 정책·전송 크기 제한은 동기화 개발 시 확정한다.

## 충돌·삭제 정책

- settings: 필드 단위로 서로 다른 변경을 병합한다. 같은 필드의 상충은 인과/기준 revision으로 판단하고 해결할 수 없으면 사용자에게 알린다. PC 시각의 updatedAt 하나만 비교해 전체 프로필을 덮어쓰지 않는다.
- homework: 프로필+숙제+리셋 주기를 식별한다. 증가·감소·완료 해제·N/A·초기화를 구분한 operation으로 반영한다. max(횟수) 병합은 사용하지 않는다.
- diary: 안정적인 기록 ID/원본 로그 identity로 중복을 막는다. 다른 PC에서 같은 과거 로그를 읽어도 중복 생성하지 않는다. profile_id 재배정도 명시적 변경으로 취급한다.
- deletion: 프로필/숙제/기록 삭제는 삭제 표식과 revision을 보존한다. 오프라인 PC가 오래된 복사본을 업로드해 삭제한 항목을 되살리지 못하게 한다. 프로필 삭제 후 일지의 원래 귀속은 식별 가능하게 보존한다.
- backup restore: 복원 데이터를 새 변경 세대와 비교하는 절차를 둔다. 옛 snapshot 복원으로 업로드 ACK나 deviceId를 과거 값으로 되돌리지 않는다.

## 구현 전 검증할 항목

- 저장 실패/강제 종료 시 원본과 outbox가 함께 남거나 함께 취소됨.
- 기존 캐릭터 N개 → 프로필 N개, 실제 설정값 보존, 재시도/롤백.
- 프로필 전환 후 늦은 쓰기·응답 및 기기별 활성 프로필 격리.
- 선택 대기 이벤트 재시작·세션 종료 후 보존 및 중복 처리 방지.
- 중복 operation 재전송, 다른 필드 동시 수정, 같은 필드 충돌, 숙제 횟수 감소·해제·주기 초기화.
- 삭제 후 오래된 PC 재접속, 백업 복원, 다른 계정/옛 동기화 파일과의 혼입 방지.
- SQLite online backup 또는 일관된 snapshot 절차 사용. 실행 중인 diary.db 파일만 일반 복사하여 완전한 백업이라고 간주하지 않음.

## Google 공식 제한 확인 및 미검증 항목 (2026-11-02)

이 절은 공식 문서 확인 결과이며 실제 프로젝트에 적용된 한도/실측 성능을 확인했다는 뜻이 아니다.

- Google은 2026-05-01 이후 프로젝트의 신규 quota 모델을 안내하며 기존 이용 프로젝트에는 이전 quota가 남을 수 있다고 명시한다. 우리 프로젝트의 실효 한도는 Cloud Console에서 별도 확인해야 한다.
- 공개 신규 기준: 프로젝트당 분당 1,000,000 quota units, 사용자·프로젝트당 분당 325,000 units. 메타데이터 files.get(alt=media 제외) 5, files.list/changes.list 100, 파일 생성/수정 50, 본문 다운로드 files.get(alt=media) 200 units. 일일 quota/전송량 및 과금 관련 안내도 함께 확인한다.
- 출처: https://developers.google.com/workspace/drive/api/guides/limits
- appDataFolder는 숨김 저장소이지 무료 무제한 별도 공간이 아니다. 숨김 앱 데이터도 사용자 저장 용량에 포함된다.
- 출처: https://developers.google.com/workspace/drive/api/guides/appdata 및 https://support.google.com/drive/answer/17196458?hl=en
- Drive HTTP batch는 개별 요청의 quota 비용을 없애지 않으며 파일 본문 업로드/다운로드 batch도 지원하지 않는다. 변경 데이터를 앱에서 한 묶음으로 합쳐 전송하는 것과 HTTP batch를 혼동하지 않는다.
- 출처: https://developers.google.com/workspace/drive/api/guides/performance
- files.update의 PATCH를 사용한다고 임의 JSON 파일 내용의 일부만 서버가 자동 병합하는 것은 아니다. 변경 기록 묶음과 snapshot 병합은 앱이 설계한다.

### 규모 산정 예 (실측 아님)

동시 실행 PC 1,000대가 30초마다 확인하면 분당 2,000번의 확인 요청이다. 신규 quota 기준으로 매번 files.list를 한 번 호출하면 분당 200,000 units, 파일 ID를 기억하고 작은 manifest의 메타데이터를 files.get으로 한 번 확인하면 10,000 units다. 후자는 내용 다운로드·쓰기·재시도 비용이 제외된 유휴 확인 비용일 뿐이다. 원격 파일 수만큼 확인 요청을 곱하는 구조는 피한다.

### 설계에 반영할 원칙

- 로컬 저장은 인터넷과 독립. UI 조작은 로컬 commit 이후 완료하며 Google 응답을 기다리지 않는다.
- 실제 동기화가 켜지는 단계에서 전송 시작 지연(예: 연속 변경 3~5초 묶음), 최대 지연, 기기당 호출 예산을 실측으로 정한다. 호출 주기를 지금 검증된 성능 수치처럼 확정하지 않는다.
- 유휴 상태에서는 작은 변경 지표를 확인하고 변경이 있을 때 필요한 데이터만 다운로드한다. 파일 ID를 보관하고 매번 전체 목록을 조회하지 않는다. 프로필마다 독립 폴링하지 않는다.
- 원격 파일을 이벤트 하나마다 무한 생성하지 않는다. 변경 묶음의 크기/개수 제한, snapshot 통합, 보관 정책을 설계한다. 삭제 표식과 기기 ACK를 보존하여 통합 후 오래된 PC가 기록을 되살리지 못하게 한다.
- 모험일지가 커져도 작은 숙제 변경에 전체 일지 전송이 따라붙지 않도록 전송 단위를 분리한다. DB 바이너리를 그대로 동기화하지 않는다.
- 부족한 저장공간/403·429·네트워크 실패는 로컬 데이터를 유지한 채 동기화를 지연시키고 재시도한다. 임의 데이터 삭제·원격 초기화로 우회하지 않는다.
- 2026-11-02 로컬 파일 metadata 참고: config.json 64,609 bytes, diary.db 2,641,920 bytes. 전체 DB 크기이며 압축·선별된 원격 payload 크기 또는 실제 성장률을 뜻하지 않는다.

### 최종 적합성 검증에 아직 필요한 증거

- 실제 Google 프로젝트의 quota/사용량/과금 설정.
- 대표 사용자 데이터의 직렬화·압축 크기 및 1일/1년 증가량.
- 실제 Google 계정으로 최초 복원·작은 변경·다중 프로필·동시 PC·장기 오프라인 복귀의 지연과 호출 수. 평균과 느린 구간(p95)을 함께 기록.
- 100/1,000/10,000 동시 PC 가정의 호출·전송량 예산과 여유율, 실패/재시도 포함 수치.
- 기록 누락·중복·충돌·중단 복구 테스트. 빠르다는 이유로 정확성을 희생하지 않는다.

판단: 혼합 로컬 구조는 현재 요구에 적합한 추천안이지만, 위 검증 전 Google 속도·용량·규모 한도까지 검증된 최선이라고 단정하지 않는다.

## 동시 사용 전제 보완

같은 게임 계정의 동시 접속 제한과 앱 프로필의 동시 사용은 별개다. 사용자는 다른 게임 계정을 두 PC에서 하나의 프로필로 선택하여 숙제 없이 모험일지를 모을 수 있다. 따라서 같은 프로필의 동시 원본 기록 합집합 병합, 고유 ID로 재전송 중복 방지, 기기/세션별 HUD 격리를 지원한다. 설정·숙제·삭제처럼 같은 값을 수정하는 경우는 기록 추가와 구분하여 충돌 정책을 검증한다. 상세 요구는 profile-sync-lifecycle.md를 따른다.

## 결정 ① — 혼합 저장과 기존 DB 이전 (확정)

- config.json은 기기 전용 설정, app-data.db는 프로필·캐릭터 설정·휴대 가능한 공통 설정·숙제·일지·미배정 기록·변경 이력의 원본이다. 동일 값의 원본을 양쪽에 두지 않는다.
- 기존 config.json과 diary.db를 일관된 snapshot으로 백업한다. 기존 DB를 기반으로 새 테이블/열을 추가하며 기존 일지 외 알람·측정 등 기존 데이터도 보존한다.
- 이전 데이터의 건수·금액 합계·관계 무결성 및 캐릭터→프로필 대응을 검증한 후에만 새 원본으로 전환한다.
- 이전 완료 marker/journal로 중단 후 재시도·롤백을 지원한다. 전환 전 실패는 원본을 보존한다. 새 DB 사용 후에는 구 DB를 다시 읽어 재복사하거나 양쪽에 기록하지 않는다.
- 캐릭터를 판별할 수 없는 기존 모험일지는 profile_id 미지정으로 한 번만 보존한다. 모험일지는 원격 전송 대상에서 제외한다.

## 결정 ② — PC별 Google 변경 파일 (확정)

- 각 PC는 자기 deviceId에 대응하는 변경 파일만 수정한다. 다른 PC의 파일을 직접 수정/교체하지 않는다.
- 한 PC 파일에 여러 프로필의 변경을 담을 수 있으며 각 변경은 profileId 및 데이터 항목을 식별한다. 프로필 공통 설정은 명시적인 공통 scope로 구분하고 임의 프로필에 넣지 않는다.
- 수신자는 다른 PC의 변경 파일을 읽어 아직 반영하지 않은 변경을 해당 프로필/공통 설정에 적용한다. 현재 선택 프로필은 기기 전용이며 이 파일로 전파하지 않는다.
- PC 식별자는 표시 이름이 아니라 영속적인 고유 ID다. PC 이름 변경이나 같은 이름의 다른 PC를 같은 작성자로 취급하지 않는다. 기존 PC의 백업을 다른 PC에 복원할 때 작성자 ID가 충돌하지 않도록 한다.
- 모험일지는 이 변경 파일에 포함하지 않는다.
- 변경 파일명·크기 상한·압축 임계값·기기 퇴역 처리·기준 버전 표현은 내부 상세 설계 대상이다. 보관은 아래 결정 ④, 충돌은 결정 ③을 따른다. 이벤트마다 새 파일을 무한 생성하지 않는다.

## 결정 ③ — 동일 항목 상충 처리 (확정)

사용자 확정: 다른 항목 변경 또는 인과 순서가 확인되는 변경은 자동 반영한다. 같은 기준에서 같은 항목을 서로 다르게 수정한 진짜 동시 충돌만 양쪽 값을 보존하고 사용자가 선택한다. 반복 팝업으로 플레이를 방해하지 않고 충돌 상태를 표시해 해결 화면에서 선택하게 한다. 이미 해결된 같은 충돌을 재전송 때 다시 묻지 않도록 해결 결과도 변경 이력으로 저장한다. 같은 값으로 바꾼 변경은 충돌로 묻지 않는다. PC 시각만으로 더 최신이라고 판정하지 않는다. 인터넷 기준 시간 및 신뢰 상태·버전 정보로 순서를 확정할 수 없는 예외에서만 사용자 선택을 받는다.

## 결정 ③-A — 변경 시각의 시간 기준 (확정)

- 사용자 확정: 변경 시각은 인터넷 시간 기준으로 보정하고 UTC로 저장한다. 타임존은 표시용 보조 정보일 뿐 PC 시계 오차 보정 수단으로 사용하지 않는다.
- 앱 내부 시계를 사용하고 Windows 시스템 시간이나 사용자의 시간 서버 설정을 임의 변경하지 않는다.
- 앱 시작·절전 복귀·네트워크 복구 시 인터넷 시간 기준을 갱신하는 방향으로 구현한다. 각 저장마다 네트워크를 호출하지 않고 보정 시각과 단조 경과시간을 사용한다. 재조회 주기·시간 제공 서비스·타임아웃은 실제 정확도/가용성 검증 후 정한다.
- 수정 시점의 changedAt과 업로드 시점은 별도로 기록한다. 늦게 업로드됐다는 이유로 과거 변경을 더 최신으로 바꾸지 않는다.
- 시간 출처·마지막 보정 시점·추정 오차/신뢰 상태를 함께 보존한다. 재시작/장기 오프라인/절전 후 검증되지 않은 PC 시각을 인터넷 시간으로 표시하지 않는다.
- 인터넷 시간 실패 시 로컬 저장·플레이를 막지 않고 변경 ID·기기 순번·기준 버전을 보존한다. 불확실한 과거 시각을 나중 업로드 시간으로 보정해 확정하지 않는다.
- 인터넷 시간 도입은 고유 변경 ID·버전 정보·중복 방지·삭제 표식의 대체가 아니다.
- 시간 신뢰도가 부족하거나 오차 범위가 겹치고 버전으로도 순서를 확정할 수 없는 동일 항목 상충은 양쪽 값을 보존한 뒤 사용자 선택을 받는다(확정).

### 예외 충돌 안내의 발생 조건 (확정 보완)

- 인터넷 미연결·시간 조회 실패만으로 충돌 안내를 생성하지 않는다. 최근 보정 기준으로 신뢰할 수 있는 시간/버전이 남아 있으면 이를 사용한다.
- 안내 대상은 동일 scope/profileId/항목에 서로 다른 유효한 변경이 있고 버전으로 선후 관계를 확정할 수 없으며, 신뢰할 수 있는 시간으로도 정책상 우선 변경을 확정할 수 없는 경우다.
- 예: 두 PC 모두 이전 상태를 가진 채 동일 필드를 다르게 수정했고 한 PC는 새로 부팅한 오프라인 상태라 보정 시간 기준이 없는 경우. 또는 동일 항목의 독립 변경 시각이 추정 오차 범위 안에 겹친 경우.
- 실제 발생 빈도는 아직 측정하지 않았다. 드문 예외 처리로 설계하되 발생률 수치나 “절대 발생하지 않음”을 보장하지 않는다.
- 플레이 도중 강제 모달/반복 팝업 대신 상태 표시와 해결 화면을 제공한다. 충돌 전 사용 중인 확정값을 유지하고 미해결 후보는 모두 보존한다. 다른 비충돌 데이터의 저장·동기화는 계속한다.
- 해결 선택은 양쪽 후보를 알고 선택한 새 변경으로 저장하여 각 PC가 같은 결론에 도달하게 한다. 같은 충돌 재수신/재시작으로 반복 확인하지 않는다. 해결 후의 새로운 상충 변경은 별도로 판정한다.

## 결정 ④ — 변경 이력 자동 정리 (확정)

- 반영이 완료되고 복원/중복 방지에 필요한 기준 상태가 확보된 변경 이력은 현재 상태 snapshot으로 통합하여 자동 정리한다. 사용자에게 정리 작업을 반복 요구하지 않는다.
- 미전송·미확정·미해결 상충 변경과 필요한 삭제 표식/중복 방지/기준 버전 정보는 정리 대상에서 제외한다. 날짜가 지났다는 이유만으로 삭제하지 않는다.
- 장기 미접속 PC는 유지된 기준보다 오래된 데이터를 무조건 업로드하지 않는다. 최신 기준을 받은 후 해당 PC의 미전송 변경을 보존해 병합/예외 충돌 해결한다.
- 구체적인 크기/개수/기간 임계값과 최소 ACK/기준 정보는 동기화 프로토콜 및 측정에서 검증한다. 이번 합의는 자동 정리 원칙이며 특정 일수 후 강제 삭제를 승인한 것이 아니다.

## 결정 ⑤ — 마지막 프로필 삭제 (확정)

- 마지막 프로필도 삭제할 수 있다. 해당 프로필과 숙제는 삭제하고 새로운 ID의 빈 기본 프로필을 정확히 하나 생성한다.
- 기존 모험일지는 삭제된 프로필의 귀속을 식별할 수 있게 보존한다. 새 기본 프로필에 재배정하지 않고 삭제한 ID도 재사용하지 않는다.
- 새 빈 기본 프로필은 이름·서버 설정 완료 전 초안이다. 신규 설치와 같은 필수 설정 흐름을 따르고 원격에 임의의 완성 프로필로 업로드하지 않는다.
- 삭제와 새 기본 프로필 생성은 한 로컬 트랜잭션으로 확정한다. 실패 시 기존 프로필을 유지한다. 이후 다른 PC 변경 수신/재시작으로 빈 기본 프로필을 반복 생성하지 않는다.

## 결정 ⑥ — 자유로운 프로필 이름과 채팅 에타 조회 (확정, 2026-11-03 보완)

- 이름은 사용자가 구분하기 편하게 정하는 표시 이름이다. 실제 캐릭터 이름을 입력받거나 프로필 이름과 일치하도록 요구하지 않는다.
- 기존 userServer 값 선택은 필수다. 이 서버로 채팅로그에 등장하는 실제 닉네임의 에타를 조회한다. 프로필 이름은 에타 조회 키가 아니다.
- 생성/수정 화면에 에타 자동 조회·조회 버튼을 넣지 않는다. 채팅 에타 실패 때문에 숙제·일지 저장을 막지 않으며 서버 변경 후 늦은 이전 서버 응답은 적용하지 않는다.

## 결정 ⑦ — Google 최초 연결의 기존 데이터 (확정)

- 로컬과 원격에 모두 데이터가 있으면 자동 덮어쓰기하지 않는다. 가져올 데이터·병합 범위 및 로컬 유지 범위를 안내하고 사용자 선택 뒤 적용한다.
- 사용자 선택 전에는 초기 빈 프로필을 원격 데이터에 덧붙이거나 로컬 전체로 원격을 초기화하지 않는다. 현재 선택된 로컬 프로필에서의 작업은 보존한다.
- 최초 복원/병합에 필요한 안전 백업·부분 실패/중단 복구를 구현하고, 옛 동기화 형식의 자동 수용은 하지 않는다. 이 기능은 향후 Google 동기화 재개발 때 구현한다.

## 로컬 기록 저장 구현 (2026-11-03)

- 일지 모듈은 `connectApplicationData`로 동일 SQLite 연결을 사용한다. 연결을 닫거나 복원 잠금 후 다시 열어도 app-data.db만 사용하며 원래 diary.db로 폴백하지 않는다. 열 때 schema와 이전 완료 marker를 확인한다.
- 일지 스키마 user_version=9에서 기록 귀속 필드, 프로필별 숙제/알람 중복 키, 날짜 통계 `diary_profile_days`를 관리한다. 프로필 저장소 app_meta schema_version=1과는 독립적이다. 기존 날짜 통계는 미배정으로 한 번만 보존하고 전체 날짜 요약은 프로필별 합산을 유지한다.
- 금화·엘소 journal v2는 입력 당시의 프로필·기기·세션 및 operation ID를 저장한다. v1의 소유자는 추정하지 않는다. 선택 변경/원래 프로필 삭제/재시작과 무관하게 원래 귀속으로 한 번만 반영한다. 복수 기기·세션의 날짜 합계는 해당 provenance만 null로 표시한다.
- 대기 이벤트의 외부 DB transaction에서는 금화·엘소도 즉시 같은 DB에 기록한다. 실패를 상위로 전달해 일지·프로필 저장·ACK가 함께 rollback되며, DB 실패를 단순 false 결과로 삼켜 ACK하지 않는다. 외부 transaction 중 대기 버퍼 flush/연결 닫기도 차단한다.
- 저장·합산·보스/숙제 중복 판단·자동 기록 교체는 프로필별이다. 전체/프로필/미배정 조회와 월간 통계·수익·내보내기가 같은 범위를 따른다. 전체 보기에 현재 프로필의 득템 키워드를 일괄 적용하지 않는다. 삭제된 프로필처럼 설정이 없으면 보존된 원본을 표시한다.
- 과거 worker의 금화·엘소·마정석 날짜 합계에도 프로필별 source ID를 제공한다. 원본 바이트 구간의 귀속이 다르면 중복 복원/암묵 재배정하지 않으며 같은 프로필의 완료 snapshot 재구성은 허용한다. 구형 미배정 일 합계는 원본을 남기고 첫 전체 분석에서 기준량을 빼 차액만 기록한다.
- 저장/조회 계층의 구현이며 실제 앱 부팅 조립, 파서/수동 기록/조회 UI/백업 연결은 별도 통합 단계다. 실제 사용자 폴더 이전은 아직 실행하지 않았다. 검증은 `check-profile-diary.ts`, `check-profile-storage.ts`, `check-magic-stone-revenue.ts`, `check-refactor-regressions.ts` 및 `docs/development/profile-storage.md`를 따른다.

## 과거 로그 복원 저장 구현 (2026-11-03)

- `profile_log_sync_state(profile_id,file_key,state_json)`: 프로필별 확정 offset·정책·누적 집계. 다른 프로필의 완료 offset을 그대로 승계하지 않는다.
- `profile_log_sources(file_key,state_json)`: 같은 파일이 커져도 안정적인 이벤트 ID를 유지할 공통 fingerprint probe.
- `profile_log_source_ranges(fingerprint,start_offset,end_offset,profile_id)`: 이미 처리한 원본 구간의 최초 귀속. NULL은 기존 미배정 구간이며 프로필 삭제 뒤에도 보존한다.
- `profile_log_legacy_aggregates(fingerprint,profile_id,value)`: 출처 위치 없는 구형 미배정 마정석/엘소/금화 합계의 차감 기준. 첫 완전 분석이 성공하기 전에는 부분 귀속을 확정하지 않는다.
- 네 테이블은 app_meta schema_version=1의 추가 로컬 표로 재열기 때도 준비한다. Google outbox/변경 이력에 넣지 않으며 DB ZIP 백업과 함께 보존한다. 구형 `chat-log-sync-state.json`은 읽기 전용 증거로만 사용한다.
- 구형 JSON의 증거는 DB를 준비할 때 `app_meta.legacy_chat_log_sync_state`에 한 번 보관한다. 이후 현재 PC의 JSON이 없어도 같은 기준을 사용한다. 구형 일지 영역만 선택 복원하면 네 진행 표와 이 증거를 함께 비우며, 설정만 복원하거나 새 DB 전체를 복원할 때는 유지한다.
- 복원 시작 ID/설정/세션을 고정하고 기록·구간·확정 위치를 같은 transaction으로 commit한 뒤 ACK한다. 손상 진행 정보는 빈 상태로 재분석하지 않고 거부한다. 일반 부팅에도 같은 경계를 적용하며 검사는 `test:profile-log-restore`와 개발 진행 문서를 따른다.

프로필 앱 수명 통합은 `profileApplication.ts`와 `profileLogSource.ts`를 사용한다. 1분/종료 checkpoint, ZIP 중지/실패 이어받기, 실시간 원본 구간과 배정 대기 제외, `profile_event_receipts`의 30일 완료 원문 압축은 개발 진행 문서의 2026-11-04 계약을 따른다. 새 Google 전송은 활성화하지 않는다.

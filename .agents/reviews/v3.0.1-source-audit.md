## 1. 요약

`v3.0.1` 태그와 `main` HEAD가 같은 커밋인지 확인한 뒤 저장소의 실행 경로와 렌더러 진입점을 정적 분석하고, 타입 검사·전체 테스트·스트레스 테스트 및 독립 재현 probe를 실행했다.

P0 결함은 확인되지 않았다. 다만 배포 전 해결이 필요한 P1 결함 8건을 포함해 총 20건이 확인됐다.

| 심각도 | 건수 | 의미 |
|---|---:|---|
| P0 | 0 | 즉시 악용 또는 광범위한 복구 불능 장애 |
| P1 | 8 | 데이터 유실, 신뢰 경계 위반, 배포 보류 수준 결함 |
| P2 | 7 | 정상 사용 흐름에서 발생하는 기능·복구·접근성 결함 |
| P3 | 5 | 구조적 부채, 성능 낭비, UI 마감·문서 문제 |
| **합계** | **20** | 미해결 상태 |

가장 먼저 처리해야 할 영역은 다음과 같다.

1. 클라우드 설정 dirty 상태 보존과 재인증 충돌
2. 로컬·클라우드 복원의 백업 및 캐시 무효화 계약
3. 관리자 권한 프로세스의 외부 바이너리 설치·실행 경계
4. 업데이트와 알림의 HTML 삽입 경로
5. Windows 포커스, XP 통계, 설정 ESC 등 사용자 흐름

## 3. P1 결함

### AUD-301-01. 원격 변경 충돌 시 업로드 대기 중인 로컬 설정 소실

**영역:** 클라우드 동기화 / 데이터 정합성
**확신도:** 10/10

원격 요청이 시작된 뒤 변경된 키만 `settingsKeysChangedDuringRequest`에 남긴다. 요청 전에 이미 dirty였던 키는 원격 snapshot으로 덮인 뒤 dirty 목록에서도 제거된다. 업로드 경로도 먼저 `reconcileRemoteBeforeUpload()`를 호출하므로 원격 revision이 달라진 순간 로컬 변경과 업로드 의도가 함께 사라질 수 있다.

독립 probe 결과:

```text
pull 전: { userServer: 3, dirty: ['userServer'] }
pull 후: { userServer: 2, dirty: [] }
```

근거:

- [`cloudSyncManager.ts:474`](../../src/modules/cloudSyncManager.ts#L474)
- [`cloudSyncManager.ts:490`](../../src/modules/cloudSyncManager.ts#L490)
- [`cloudSyncManager.ts:623`](../../src/modules/cloudSyncManager.ts#L623)
- [`cloudSyncManager.ts:650`](../../src/modules/cloudSyncManager.ts#L650)

권장 수정:

- 요청 전 dirty snapshot과 요청 중 추가된 dirty의 합집합을 보존한다.
- dirty 키는 해당 값의 원격 업로드가 성공한 뒤에만 제거한다.
- `local edit → remote revision change → reconcile → upload` 통합 테스트를 추가한다.

### AUD-301-03. 로컬 백업 복원 후 클라우드 검증 캐시 미무효화

**영역:** 로컬 복원 / 클라우드 수렴
**확신도:** 9/10

수동 로컬 백업에는 `cloud-sync-state.json`이 포함되지 않으며, 복원 성공 후 기존 remote revision과 fingerprint를 무효화하지 않는다. 재시작 자동 pull은 현재 로컬 checksum을 확인하지 않고 원격 fingerprint가 같다는 이유로 `unchanged` 처리할 수 있다.

오래된 로컬 백업을 복원하면 로컬·원격이 다른 상태로 남고, 다음 로컬 변경이 오래된 값을 원격에 다시 올릴 수 있다.

근거:

- [`localSnapshot.ts:31`](../../src/modules/localSnapshot.ts#L31)
- [`backupManager.ts:171`](../../src/modules/backupManager.ts#L171)
- [`cloudSyncManager.ts:131`](../../src/modules/cloudSyncManager.ts#L131)
- [`cloudSyncManager.ts:870`](../../src/modules/cloudSyncManager.ts#L870)

권장 수정:

- 수동 복원 완료 시 remote revision/fingerprint와 base snapshot을 무효화한다.

- 캐시 재사용 조건에 로컬 checksum 또는 restore epoch를 포함한다.

### AUD-301-06. 관리자 권한으로 검증되지 않은 사용자 경로 실행 파일 실행

**영역:** 권한 분리 / 외부 바이너리 / 공급망
**확신도:** 10/10

Windows 빌드는 `requireAdministrator`로 앱 전체를 실행한다. AI 분석용 `llama-server.exe`는 사용자 쓰기 가능 경로인 `userData/bin`에 저장되고 존재 여부만 확인한 뒤 실행된다.

다운로드·설치 경로에는 다음 보호가 없다.

- SHA-256 또는 서명 검증
- 요청 timeout과 최대 크기 제한
- 실제 single-flight lock
- 격리 디렉터리에서의 파일 allowlist 검증
- 디렉터리 단위 원자 교체

서버 ZIP은 응답 전체를 메모리에 모은 뒤 최종 실행 디렉터리에 `-Force`로 압축 해제한다. 중단이나 중복 호출 시 EXE와 DLL이 서로 다른 세대로 섞일 수 있다.

## 5. P3 결함

### AUD-301-16. 채팅 오버레이 최소 높이 계약 불일치

renderer와 창 sizing 정책은 최소 높이를 80px로 보지만 실시간 resize IPC는 120px 미만을 거부한다. 80~119px 구간에서 드래그 중 창이 따라오지 않다가 mouseup의 최종 설정 적용 시 점프한다.

### AUD-301-17. 리사이즈 mousemove마다 IPC와 native setBounds 실행

채팅·집중 대화 창은 모든 mousemove를 renderer에서 main IPC로 보내고 즉시 `BrowserWindow.setBounds()`를 호출한다. 설정 파일 쓰기는 debounce되지만 IPC, native layout과 config clone은 coalescing되지 않는다.

### AUD-301-18. 게임 오버레이 스톱워치가 10ms마다 DOM 갱신

스톱워치 실행 중 `setInterval(..., 10)`으로 초당 최대 100회 text를 갱신한다. 창은 `backgroundThrottling: false`이며 동일 표시 문자열인지도 확인하지 않는다.

`webPreferences`를 병합한 뒤 `...extraProps`를 적용한다. 호출자가 `webPreferences`를 넘기면 이미 병합한 preload, `contextIsolation`, `nodeIntegration`, `backgroundThrottling` 기본값 전체가 다시 덮인다. 현재 splash caller는 핵심 보안 옵션을 다시 지정하지만 helper의 공통 기본값 계약은 지켜지지 않는다.

권장 수정: `webPreferences`를 `extraProps`에서 구조 분해하고 나머지 속성을 먼저 펼친 뒤 최종 병합한 `webPreferences`를 마지막에 배치한다.

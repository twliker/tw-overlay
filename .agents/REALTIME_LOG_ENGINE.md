# 실시간 채팅 로그 처리와 과거 로그 복원

TW-Overlay는 테일즈위버 채팅 로그 파일에 새로 추가된 줄만 추적해 알림과 일지 기능에 전달합니다.

## 처리 흐름

1. 설정된 채팅 로그 폴더와 현재 날짜 로그 파일을 확인합니다.
2. 마지막으로 처리한 위치 이후의 새 로그만 읽습니다.
3. 인코딩과 로그 형식을 검증한 뒤 채팅, 경험치, 득템, 숙제 및 버프 이벤트로 분류합니다.
4. 이벤트를 오버레이, 알림, 숙제 체크리스트와 모험 일지에 전달합니다.

`chatLogManager.ts`는 감시와 읽기 위치를 관리하고 `chatParser.ts`는 이벤트를 생성합니다. `chatLogProcessor.ts`는 채팅을 표시하고 `ProfileService`는 자동 기록의 세션과 프로필을 확정합니다. 선택 전에도 채팅을 계속 표시하며 자동 기록의 원본은 선택할 때까지 보관합니다. 이전 세션 수동 배정에서는 과거 경험치·버프·현황판과 소리를 재생하지 않습니다.

앱이 종료되어 있던 기간의 로그는 과거 로그 동기화 기능으로 다시 분석할 수 있습니다. 기본 동기화는 아직 완료되지 않았거나 이후 내용이 추가된 파일만 이어서 처리합니다.

**일지 보관 → 영구 보관**을 선택하면 날짜 제한 없이 현재 채팅 로그 폴더에 남아 있는 과거 원본을 복원할 수 있습니다.

**이미 동기화한 로그도 다시 분석**을 체크하면 보관 기간 안의 완료 파일을 처음부터 읽습니다. 프로필 저장소는 누락된 개별 득템·SEED를 원본과 대응해 복구하며 수동 일지와 원본 소유권을 보존합니다. 오늘 로그는 동기화 시작 시점까지의 완전한 줄을 먼저 처리하고, 그동안 새로 들어온 줄부터 실시간 감시로 이어갑니다. 파일이 교체되거나 안전하게 이어받을 수 없으면 기존 기록을 보존합니다.

이전 단일 저장 방식의 복원은 메인 캐릭터를 대상으로 합니다. 해당 호환 경로는 공개 가이드에서 설명하는 현재 프로필 모드와 별도로 `check-refactor-regressions.ts`에서 검사합니다.

현재 앱에서는 복원 시작 시 선택한 프로필에 숙제와 일지를 반영합니다. 시작 전 대상 이름과 서버를 표시합니다. 이미 복원한 구간과 기존 미배정 기록은 원래 귀속을 유지하며, 이후 추가된 구간은 새로 선택한 프로필로 복원할 수 있습니다. 외치기 기록은 공통입니다.

복원 중에는 프로필 전환·삭제와 해당 설정·숙제 편집을 잠급니다. 그동안 새로 감지한 자동 기록은 보관했다가 완료 후 원래 플레이 세션에 반영합니다. 저장 실패 시 기존 기록과 재시도에 필요한 정보를 보존합니다.

사용 흐름은 [환경설정 가이드](../docs/settings.md#과거-채팅-로그-복원)를 따릅니다.

어벤던로드 입장료 지불 로그도 과거 분석 시 음수 SEED로 복원합니다. 이미 처리한 파일까지 확실히 재구성하려면 **이미 동기화 완료된 로그도 다시 분석하여 자동 기록 재구성**을 선택합니다. 보관된 원본 로그가 없는 지출은 복원할 수 없습니다.


오늘 로그의 복원 범위에는 마지막 행에 개행이 없어도 `</br>`로 완전히 닫힌 줄이 포함됩니다. 작성 중인 행과 범위를 확정한 뒤 닫힌 줄은 실시간 이어받기로 처리합니다. 회귀 검사는 `test:profile-log-restore`와 `test:profile-lifecycle`에서 확인합니다.

파일 날짜 헤더는 `parseChatLogDateHeader`만 판정한다. 시각 태그 `[ HH시 mm분 ss초 ]`가 없고 줄 전체가 `Date : YYYY-MM-DD` 또는 `Date : YYYY년 M월 D일`인 줄만 헤더이며, 채팅 본문의 "Date :"는 파서 날짜를 바꾸지 않는다(회귀: `test:profile-recording`).

실시간 감시 북마크 저장 실패는 읽기를 멈추지 않는다(`saveWatchBookmark`). DB에는 마지막으로 저장에 성공한 위치가 남고 다음 읽기에서 다시 저장하며, 재시작하면 그 위치부터 at-least-once로 다시 읽는다(회귀: `test:profile-lifecycle`). 남은 한계: `prepareProfileLogSource` 쓰기가 실패하면 새 파일 감시를 시작하지 못하고 재연결 경로로 간다.

실시간 읽기 한 번(`watchLog`의 read)에서 나온 프로필 기록은 그 읽기 안에서 모아 `ProfileService.acceptLiveLines`로 한 commit에 저장·반영한다. 대기 원본과 반영(ACK)을 같은 transaction에 두되 기록마다 savepoint로 반영해, 소비자 실패는 그 기록만 대기에 남겨 재시도하고 북마크는 진행한다. 묶음 commit이 실패하면 줄별로 기존 저장 재시도 대기열에 넣는다(상한·북마크 고정 규칙은 줄 단위 그대로). 기믹 알림은 해석 중 즉시 처리하므로 묶음과 무관하다. 회귀: `test:profile-recording`, `test:profile-lifecycle`.

경험치 줄(정수 교환이 아닌 것)만 있는 읽기는 DB에 쓰지 않는다(사냥 정보는 DB에 줄 단위로 남기지 않는다). 처리 구간은 메모리(`ApplicationData.deferAppliedRange`)에서 늘리고, 기록이 있는 읽기(같은 commit)·1분 체크포인트·구간을 읽는 모든 호출·종료 때 쓴다. 감시 북마크도 그동안은 최대 1분 간격으로 저장한다(먼저 구간을 써서 북마크가 구간을 앞서지 않게). 비정상 종료하면 마지막 체크포인트 뒤 최대 1분의 경험치·처치 수만 HUD에서 빠지고 일지·중복에는 영향이 없다(2026-11-25 사용자 결정). 재시작 복구 읽기·세션 경계처럼 소유자를 확정할 수 없는 경험치 줄은 미배정 대기로도 남기지 않는다(배정해도 기록·HUD 재생이 없어 미배정 목록만 늘린다). 버프 등 다른 진행 줄은 바로 쓴다. 회귀: `test:profile-durability`, `check-profile-crash`. 실제 사냥 측정: `--mix tw --rate 2.3 --writer spread`.

같은 읽기 범위의 commit은 `ApplicationData.withRelaxedDurability`로 WAL `synchronous=NORMAL`(commit마다 flush 없음)로 확정하고, 그 밖의 저장은 FULL을 유지한다. 정전 때는 flush되지 않은 마지막 commit들이 북마크와 함께 사라지고, 다음 실행이 되돌아간 북마크부터 원본을 다시 읽어 이벤트 ID로 중복 없이 기록한다. 기기 설정 JSON을 함께 바꾸는 `commitConfiguration`은 범위 안에서도 FULL이다. 되돌아간 구간은 재시작 복구 읽기라 소유자를 확정할 수 없어, 그 사이 득템·SEED·숙제 줄은 자동 기록되지 않고 **미배정**으로 돌아온다(사용자가 배정. v3.3.5 FULL에서는 그대로 기록돼 있던 줄이다). Google 업로드 전에는 `ProfileSyncCoordinator`의 FULL commit(`setMeta('uploadSizing')`)이 먼저 있어야 한다. WAL은 한 파일이라 그 flush가 앞의 NORMAL commit까지 디스크에 확정하므로, 올린 변경이 정전으로 로컬에서 사라지지 않는다(순서가 깨지면 다음 수신에서 "작성자 되돌림"으로 계정 연결이 풀린다. 회귀: `check-refactor-regressions.ts`의 `checkProfileUploadDurableOrder`). 회귀: `test:profile-durability`(정전 시점 DB 복사본으로 재시작). 측정: `npm run bench:runtime`(v3.2.2 태그 빌드와 같은 사냥 로그 비교).

프로필이 선택돼 바로 반영할 수 있는 줄은 대기 원문(`pending_profile_events`)·HUD 복원 대기 행 없이 결과(일지·숙제)와 처리 구간 표 `log_ranges`의 반영(applied) 구간(원본 파일 `log_files`별 byte 구간, 겹치지 않음. 한 행은 최대 256KB. 파일은 경로와 무관한 내용 키로 정하고 경로별 지문은 `log_file_aliases`로 연결해, 다른 폴더의 복사본도 같은 파일이다)만 같은 commit에 남긴다(`ProfileService.acceptLiveLines`, 줄 단위 savepoint). 일지·숙제에 실제로 남는 줄은 줄 귀속(`profile_log_line_owners`, live=1)도 남긴다(경험치 줄은 만들지 않음). 획득 줄은 지금 설정으로 일지에 남는 줄(등록 아이템·경험의 정수·엘소·금화 주머니)만 남긴다(`itemAcquisition.recordsLootLine`). v3.3.5는 자기 획득 줄 전부에 남겼다(실제 사냥 로그 하루 기준 등록하지 않은 아이템 줄 약 200~700행, 37~110KB를 줄임). 사냥 중 엘소 스크롤 줄은 일일 엘소 누적에 남는 기록이라 귀속을 유지하며, 남은 줄 귀속(하루 3,500~6,800행)의 대부분이다. 등록 아이템을 나중에 추가하면 재분석이 그 줄을 새로 기록할 수 있다(그때까지 일지에 없던 줄이라 중복 아님). 30일 영수증 정리의 보관 범위는 그대로 자기 획득 줄 전부다(설정이 바뀌어도 그때 기록한 줄의 증거를 지우지 않게). 기록 없는 채팅만 읽은 동안은 commit하지 않고 다음 기록 줄의 commit이 이어 붙인다(`chatLogManager.liveSpan`). 재읽기 중복 방지는 이벤트 행 → 처리 구간(줄 시작 byte) → 줄 귀속(live=1) 순이다. 미배정·재시도·반영 실패 줄은 이전처럼 대기 행으로 남고 범위를 끊는다. 대기 행은 미룬 동안만 두며, 완료(반영·무시)되면 1분 압축 때 그 줄을 처리 구간(applied·ignored)으로 바꾸고 지운다(30일 원문·영수증 없음, 줄 귀속은 유지). 변환은 이어지는 줄을 한 구간으로 합쳐 쓰고, 구간마다 120ms 예산을 확인해(commit 포함 1분에 약 150ms, 구간 하나는 항상) 처리한다. 파일 크기·핸들은 한 번 압축 안에서 재사용하고(`LogFileProbe`), 앞·겹치는 구간은 끝 위치 인덱스(`idx_log_ranges_end`)로 찾는다(실제 v3.3.5 DB는 평균 2.19행마다 끊긴다. 측정: `npm run bench:convert`). HUD는 바로 반영·미룬 구간 쓰기가 새로 채운 구간만 `profile_runtime_ranges`에 남기고 1분 체크포인트가 비운다. 비정상 종료 뒤에는 남은 구간만 원본에서 다시 읽어 진행만 재생한다(`recoverLiveProgress`). 재생 순서는 HUD 대기 행 전부 → 원본 구간이라 시간 순이 아니다(대기 경로 도전과제 시작 줄과 바로 반영한 경험치 줄이 섞이면 복원에서만 순서가 바뀔 수 있음, HUD 최대 1분). 저장 재시도를 거친 줄과 미배정으로 읽은 줄은 바로 반영 구간이 덮지 않는다(`chatLogManager.liveSpan`). 프로필을 지우면 그 프로필의 HUD 복원 구간도 지운다. 복원·원문 변환·이전 세션 배정이 만든 반영 구간은 HUD에 재생하지 않는다. 과거 로그 복원은 자기 범위를 알려진 줄로, 다른 프로필 범위를 제외 구간으로 본다. 복원도 이 프로필이 처리한 구간을 반영 구간으로 남기고(줄 귀속도 함께), 시작할 때 파일이 다른 내용으로 바뀐 구간(끝 표본 불일치)을 행 단위로 지운다. 실시간 감시가 파일 교체·절단을 감지해 처음부터 다시 읽으면 읽은 범위와 그 파일의 미룬 구간을 버리고, 지금 파일보다 끝이 긴 구간은 쓰지 않는다. 앞부분이 그대로인 짧은 파일로 바뀌면 바뀐 지점이 걸친 행과 그 뒤만 다시 읽으며, 그 안의 일지·숙제 줄은 줄 귀속으로 걸러지고 경험치는 HUD에 한 번 더 들어갈 수 있다(회귀: `test:profile-log-replace`). 실시간 자동 기록 행은 원본 위치(`activity_logs.source_file_id`, `source_offset`)를 갖고, 재분석은 그 위치의 행이 없고 사용자 삭제 표식(`diary_deleted_sources`)도 없으면 다시 만든다. 회귀: `test:profile-durability`, `test:profile-lifecycle`, `test:profile-crash`, `test:profile-storage`, `test:profile-log-replace`.

오늘 로그 메모리 창(`_todayLines`)은 시작 모드와 관계없이 `MAX_RECENT_HISTORY_CHARS`를 넘으면 오래된 줄부터 정리한다(회귀: `check-refactor-regressions.ts`).

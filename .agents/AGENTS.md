# TW-Overlay 에이전트 개발 수칙

이 문서는 TW-Overlay 저장소에서 작업하는 모든 에이전트가 따라야 하는 기준입니다.

## 기준 문서

- 프로젝트 개요, 기술 스택, 디렉터리 역할과 핵심 실행 흐름은 [PROJECT_GUIDE.md](./PROJECT_GUIDE.md)를 기준으로 합니다.
- 채팅 파싱 및 시스템 메시지 색상 처리 파이프라인은 [CHAT_SYSTEM_COLOR_PIPELINE.md](./CHAT_SYSTEM_COLOR_PIPELINE.md)를 기준으로 합니다.
- UI를 추가하거나 변경하기 전에 반드시 [DESIGN_TOKENS.md](./DESIGN_TOKENS.md)를 읽고 기존 색상, 글꼴, 간격, 창 크기, Glassmorphism 규격을 유지합니다.
- 버전 변경, 설치 파일 생성, 태그 및 GitHub Release 작업은 [release_workflow.md](./release_workflow.md)를 따릅니다.
- `.gemini`는 과거 조사 자료 보관용이며 개발 규칙과 릴리즈 기준의 원본으로 사용하지 않습니다.

## 기능 및 UI 보존

- 리팩터링 작업은 기존 기능, 데이터 형식, IPC 동작, 화면 구조와 시각적 결과를 변경하지 않아야 합니다.
- UI 변경 요청이 아닌 경우 클래스, 크기, 여백, 색상, 애니메이션과 DOM 계층을 임의로 바꾸지 않습니다.
- 사용자 설정과 기존 마이그레이션 데이터의 하위 호환성을 유지합니다.
- 사용자 입력은 가능한 한 `textContent`, DOM API와 `addEventListener`로 렌더링하며, `innerHTML` 문자열과 인라인 이벤트 코드에 직접 보간하지 않습니다.

## 기능 계약 주석

- 기능별 계약 주석의 기준 위치와 함께 확인할 테스트·문서는 [development/feature-contract-index.md](./development/feature-contract-index.md)에서 관리합니다. 새 기능을 추가하거나 담당 모듈을 옮기면 이 인덱스도 같은 작업에서 갱신합니다.
- 로그 감지, 중복 제거, 설정 소유권, 리셋 주기, 데이터 기록·복원처럼 코드만 보고 여러 해석이 가능한 기능은 실제 처리 진입점에 상세한 **기능 계약 주석**을 둡니다.
- 기능 계약 주석에는 가능한 범위에서 다음을 명시합니다: 사용자가 기대하는 동작, 실제 입력·게임 로그 형태, 의도적으로 제외하는 입력과 이유, 사용하는 설정 키와 담당 화면, 저장·요약·동기화로 이어지는 후속 경로, 변경 시 함께 실행할 회귀 테스트.
- 기능을 수정하기 전에 관련 계약 주석과 테스트를 먼저 읽습니다. 구현과 주석이 다르면 어느 쪽이 맞다고 추측하지 말고 실제 로그·기존 버전·사용자 의도를 확인합니다.
- 기존 동작을 넓히거나 줄이는 해석이 둘 이상 가능하면 임의로 결정하지 않고 사용자에게 먼저 확인합니다.
- 계약 주석을 바꾸는 기능 변경은 같은 작업에서 실제 입력 기반 회귀 테스트와 사용자 문서를 함께 갱신합니다. 주석만으로 동작 보존을 대신하지 않습니다.
- 모든 함수에 구현을 그대로 번역한 주석을 반복하지 않습니다. 기능의 기준이 되는 진입점에 계약을 상세히 적고, 내부에서는 그 계약만으로 설명되지 않는 예외·순서·중복 방지 이유를 바로 옆에 적습니다.

## 소스 및 모듈 규칙

- 메인 프로세스, preload, 공통 모듈, 빌드 및 테스트 도구의 원본은 TypeScript로 작성합니다.
- HTML 내부의 화면 전용 JavaScript는 허용하지만 복잡하거나 재사용되는 로직은 `src/renderer/**/*.ts`로 분리합니다.
- 직접 작성한 `.js` 원본을 `src`와 `scripts`에 추가하지 않습니다. JavaScript는 빌드 결과물로만 생성합니다.
- 공통 상수와 타입은 각각 `src/shared`와 `src/shared/types.ts`에서 관리하고 화면·모듈별로 중복 선언하지 않습니다.
- preload에서는 임의 채널을 받는 범용 IPC API를 만들지 않고 기능별로 타입이 지정된 API만 노출합니다.
- 반복 초기화가 가능한 `start()` 계열 코드는 중복 리스너와 중복 타이머가 생기지 않도록 멱등성을 보장합니다.

## 디자인 및 가독성

- 일반 텍스트의 최소 크기는 `0.75rem`(12px), 중요 안내와 본문은 `0.875rem`(14px) 이상을 권장합니다.
- 복잡한 관리 창은 최소 `800px × 600px`, 간이 팝업과 위젯은 최소 `400px × 300px`를 기준으로 합니다.
- 어두운 배경 위 텍스트는 `#ffffff`, `#cbd5e1` 등 충분한 대비를 사용합니다.
- 임의 색상과 일회성 스타일을 추가하기 전에 디자인 토큰과 기존 공통 컴포넌트를 우선 사용합니다.

## 필수 검증

- 일반 코드 변경 후 `npm run typecheck`를 통과해야 합니다.
- 기능, UI, 파서, IPC, 빌드 구조 변경 후 `npm test`를 통과해야 합니다.
- `npm test`는 전체 빌드, 정적 회귀 검사와 실제 Electron DOM 렌더러 검사를 포함합니다.
- 사용자에게 보이는 UI를 변경했다면 자동 검사와 함께 해당 화면의 실제 표시 상태도 확인합니다.
- 브라우저에서 직접 로드하는 렌더러 번들에는 CommonJS `require` 또는 `exports` 코드가 포함되지 않아야 합니다.

## 릴리즈

- 태그를 생성하기 전에 `.agents/release_workflow.md`의 일반 자동 게이트, 관리자 권한 `npm run test:zorder:windows`, 사용자 실기 체크리스트와 최종 설치 파일 검증을 모두 통과해야 합니다.
- 미실행·실패·릴리즈 차단 코멘트가 남은 테스트를 GitHub Actions 성공이나 조건부 skip으로 대체하지 않습니다.
- `scripts`와 `dist-tools`는 빌드·테스트 도구이며 사용자 설치 패키지에는 포함하지 않습니다.
- 릴리즈 관련 명령, 문서, CI 흐름을 변경했다면 같은 작업에서 `release_workflow.md`도 갱신합니다.
- 기술 스택, 디렉터리 역할 또는 핵심 데이터 흐름을 변경했다면 같은 작업에서 `PROJECT_GUIDE.md`도 갱신합니다.
